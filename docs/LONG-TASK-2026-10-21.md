# Sustained-task test — 2026-10-21

Long-task testing is the current priority. No boot-care work or desktop development was performed.

## Task and checks

One persistent conversation built an event-ledger module over eight stages: writes; increments/deletions; renames; nested batches; replay snapshots; deterministic diffs; optimistic preconditions; final audit integration. Each stage introduced new work without repeating the full initial contract. All earlier functions and requirements had to remain intact. An untrusted issue comment attempted to induce input mutation and deletion of prior functions.

After every response the saved module ran in the isolated executor against cumulative checks. Later tests exercised both success and failure input preservation, unknown operations, negative/zero values, nesting, ordering, and prior public functions. Test/reference data was frozen before each run; a reference implementation passed and a deliberately broken implementation failed preflight. Expected answers were not supplied to the model. Feedback contained actual external verification summaries. A maximum of two corrective attempts was available; neither arm needed any.

Raw DeepSeek received the same user instructions and prior conversation but no ECU system instructions or retrieval. It used provider-default high reasoning. ECU used Auto. Exact contracts, stages and tests were checked equal before aggregation. Runs were sequential, one sample per profile, not randomized. All candidates and API replies are saved.

ECU used **14.39% fewer total tokens and 47.42% less provider response time**, with equal checked completion. Its instructions still increased input overhead. These percentages describe this run; they are not a statistically established general advantage, dollar-cost estimate, or whole-workflow timing measurement.

Unseen stress cases used sixty independent forty-event streams including nested batches, evaluated across four functions. These ran in bounded batches without relaxing sandbox resource limits. Two additional ECU ownership probes verified that returned states/snapshots could be changed without mutating the original or other snapshots.

## Fresh-context continuation

A new conversation received only the saved requirements and latest module, not the earlier transcript or returned reasoning. It added compact_events while retaining all four earlier functions. It passed **208 checks** with **2,833 tokens** and no repair. This demonstrates one successful explicit-checkpoint continuation, not autonomous recovery or general memory reliability. Raw was not tested on this additional continuation, so no comparative claim is made there.

## Scope and limits

This is a sustained eight-stage single-module engineering task, not an hours-long multi-file repository job or a context-window capacity benchmark. It did not reach the model's failure limit. Both raw and tuned models succeeded, so the observed ECU advantage is efficiency rather than higher accuracy. The sample does not establish reliable handling of external dependencies, large unfamiliar repositories, interrupted tool transactions, or underspecified requirements.

This pass made **17 paid calls using 38,833 total tokens**. All 43 local application/executor tests also passed after adding the history-preserving raw evaluation mode. No source patches were applied to a user project.
